## 一、当前体积实测（原始命令与数字）

gzip -c public/index.html | wc -c
gzip -c public/data/coins.json | wc -c
gzip -c public/_headers | wc -c
# 参考（不作预算口径）：gzip -9 -c <file> | wc -c

| 构成 | 字节（原始） | 占 index.html | 说明 |
|---|---:|---:|---|

两点必须先说清：

1. **`public/_headers` 不是传输文件**。它是 Cloudflare Pages 的响应头
   配置产物，不会被访客下载；其 2,222 B 不计入首屏传输预算，单列
   预算的理由只是控制配置膨胀与 CSP 行长（gen-headers 已有单行
   1,900 字符硬限），不要把三组数字无区别地相加当「首屏体积」。
2. **首屏实际请求不止这两个静态文件**：还有 `/api/board` 的 JSON
   响应（动态、经服务端缓存，非仓库静态文件）与 WA beacon 外部脚本
   （平台文件，不在仓库）。本预算按任务口径只管仓库静态部分；
   `/api/board` 体积归数据管线口径（board 响应大小已有线上实测先例，
   见 `ops/perf-baseline.md`），不与本线混算。

### 口径锁定（防「换量法就达标」）

- 预算一律以 **`gzip -c`（默认级别）后 `wc -c`** 为准。默认级别与
  `-9` 在本仓三文件上相差 924～945 B，混用口径足以吃掉全部余量。
- Cloudflare 边缘可能以 Brotli 等方式再压缩，实际传输通常小于上表；
  本线是**仓库产物的可复现代理指标**，不声称等于真实用户下载量。
  真实性能结论仍以 `ops/perf-baseline.md` 的 Lighthouse 口径为准
  （W4-23 干净基线另行处理，本文件不替代它）。

## 二、首屏体积预算线（定版建议）

定线原则：以当前实测为基数留 6%～9% 余量——余量要够吸收一期正常
功能迭代（若干字段/文案级改动），又要紧到「再塞一个大块功能必然
触线、必须先评审」；不引用外部站点的行业数字作依据（本站形态是
200 行全量静态注入，与一般营销页不可比）。

| 预算项 | 当前实测（gzip） | **预算线（现行）** | 余量 | 依据 |
|---|---:|---:|---:|---|
| `public/index.html` | 46,183 | **≤ 50,000 B** | 3,817 B（8.3%） | 静态 200 行占 75%，行数据由管线生成、单期波动小；余量主要留给样式/脚本/文案迭代 |
| `public/data/coins.json` | 24,513 | **≤ 27,000 B** | 2,487 B（10.1%） | 现行对象形态口径；此线仅管 W3-22 上线**之前**，上线后按下行收紧 |
| 首屏静态合计（上两项） | 70,696 | **≤ 75,000 B** | 4,304 B（6.1%） | 合计线是主线：单项不超但合计超，同样触线（防两边同时吃余量） |

### W3-22 上线后必须复核并收紧（写死触发条件）

- 站长已于 2026-11-13 拍板 W3-22 按 gzip **≤21 KB** 新线补做
  （见 `CONSTRUCTION_PHASE3.md` 站长裁决记录与 `ops/w322-assessment.md`；
  本文件把该「KB」口径明确为 **≤ 21,504 B（21×1024）gzip 后**，
  与本文件其它线统一按字节计，避免 KB/KiB 歧义——若后续批次对该线
  另有定版，以其定版为准并回填本文件）。
- W3-22（coins.json 紧凑形态）部署完成的**同一次部署核对**中：
  - `coins.json` 预算线由 ≤27,000 B 收紧为 **≤ 22,500 B**
    （21,504 B 达标线＋约 1,000 B 日常数据波动余量）；
  - 首屏静态合计线由 ≤75,000 B 相应收紧为 **≤ 71,000 B**
    （按 coins 预期降幅约 4,000 B 等额下移，index.html 单项线不变）；
  - 若 W3-22 实测未达其 21,504 B 线，则不收紧、且 W3-22 本身按其
    评估口径处置，不得用本文件的 27,000 B 旧线为其放行
    （两条线管不同的事：旧线管「别再涨」，W3-22 线管「要降下来」）。
- 同理，未来任一大块静态内容增删（如榜单行数变化、详情字段大改）
  部署时，必须同批复核本表并在文末复核记录留一行。

### 预算线的执行方式

- **现行（人工核对，立即生效）**：每次部署前，部署执行者在部署
  清单中逐字跑「一、实测命令」四行命令，把三组 gzip 数字与上表
  现行线比对：任一超线即**停部署**，先在本文件登记超线原因与处置
  （回滚改动／站长特批调线，二选一，不许先部署后补记）。
  本包不改 `scripts/deploy.sh`，故此步暂靠人工纪律；核对结果随
  该次部署记录（CHANGELOG 或施工记录）留一行数字即可。
- **未来建议（自动核对，本包只建议、不实现）**：仿
  `ops/headers/gen-headers.mjs` 的 `--check` 模式写一个零依赖
  `ops/perf/check-volume.mjs`：用 Node `node:zlib` 的 `gzipSync`
  （须先与命令行 `gzip -c` 做一次同文件对拍，确认字节数一致或
  固定差值后再定版为脚本口径）、读上表预算常量、超线以非零退出；
  再由 `deploy.sh` 在 gen-headers --check 之后调用。这样体积线与
  CSP hash 线同为部署门禁。**注意**：gzip 实现差异（命令行 gzip
  与 zlib 的头部时间戳/级别默认值）会带来个位数～数十字节漂移，
  脚本化时必须对拍定版，不得直接拿 `gzipSync` 数字套命令行口径的线。

### 拆分的收益（若拆）

1. 可维护性：659 行脚本按 S1–S12 拆为 3–5 个文件后，单文件 diff、
   评审与定位成本下降；别名表（S4 数据部分）与逻辑分离后，改别名
   不再碰逻辑文件。
2. 缓存：外置 JS 可独立于 HTML 缓存（HTML 现为 `s-maxage=60,
   stale-while-revalidate=300` 的短 SWR），回访时脚本不必随 HTML
   重下——但脚本本体仅 36 KB 原始、gzip 后更小，且 HTML 中 75%
   是每次都可能变的静态榜单行，此收益量级有限。
3. 局部测试：格式化（S2）等纯函数拆出后更易被 Node 侧单测直接
   import（现行靠桩测/快照 diff 间接覆盖）。

### 拆分的成本与风险（若现在拆）

1. **CSP hash 机制影响（核心）**：`ops/headers/gen-headers.mjs` 对
   `public/index.html` 每个无 `src` 的内联 `<script>`/`<style>` 块
   逐块算 SHA-256 拼入 CSP（现行 CSP 含 2 个 script hash＋1 个
   style hash，见 `public/_headers`）。其提取逻辑对带 `src` 的
   脚本是**跳过不算 hash、靠 `script-src 'self'` 放行同源外置文件**
   （gen-headers 提取处明注）。故拆分后：
   - 被拆走的逻辑不再受 hash 钉住，防护从「内容指纹」降为
     「同源即可」——同源目录下任何脚本文件都会被 CSP 放行，
     防护粒度实质变粗，须在安全口径上明确接受这一点；
   - 每次拆分/合并都要重跑 gen-headers 生成 `_headers` 并做
     `--check`（现行部署门禁的一部分），拆分批次与任何 CSP 变体
     切换（WA-ON/OFF）不得同批，避免归因混乱；
   - JSON-LD 块若误拆/误动，其 hash 同步变化，结构化数据可能被
     CSP 静默拦截——JSON-LD 与 `<style>` 应明确留在内联、不拆。
2. **生成管线耦合**：`public/index.html` 不是手写文件——静态 200 行
   由构建管线注入（render-snapshot 一类脚本生成并有逐行 diff 校验，
   S6 行渲染与 Python 侧同构）。拆分必须先摸清生成器对脚本区间的
   假设（按标记定位还是按整文件模板），否则拆分会在下一次管线
   重渲染时被覆盖或令 snapshot-verify 失效。这一摸底本身就是
   半个工作包的量。
3. 首屏请求数：拆 1 个脚本＝首屏多 1 次请求（同源、HTTP/2 下成本
   低但非零）；在 Slow 4G 实验室口径（见 perf-baseline）下，
   执行顺序还须保持「脚本在静态行之后、init 时序不变」，
   否则可能动到 W3-16 的并行取数与 W3-05 的原地修补时序。
4. 时机冲突：S11 解码区是 W3-22 已批准扩围的改动点、S5/S10 是
   F4-46 已定版待改的交互点（见 `ops/verification-tracker.md`）。
   现在拆分等于在两个已排期改动之前先搬一次家，两批改动都要在
   新结构上重做回归，净成本为负。

### 结论（定版）

**暂不拆。** 理由收束：脚本本体 36 KB／659 行尚未大到压垮维护
（真正的体积主体是静态榜单行，占 75%，拆脚本对首屏体积几乎
无感）；而拆分的两项硬成本——CSP 由 hash 钉住降为 `'self'` 放行、
生成管线耦合未摸底——都发生在 W3-22 与 F4-46 两批已排期改动
即将动同一文件之际，现在拆是给后续批次添乱。

**重新评估的触发条件（满足任一即重提本评估，不自动开工）：**

1. 主内联脚本本体超过 **50,000 B** 或超过 **900 行**
   （现行 36,144 B／659 行，约 1.4 倍余量）；
2. W3-22 与 F4-46 两批均已上线且稳定后，前端再有「新增独立功能区」
   级改动（如新增第二种详情视图）时，先评拆分再加功能；
3. 出现两人／两批次并行改 `index.html` 脚本区且冲突成常态时。

**若将来拆，按此预定版执行（避免临场发明）：** 只拆脚本、不拆
`<style>` 与 JSON-LD；第一刀只拆最独立的两块——S4 的 `ALIASES`
别名数据与 S2 格式化纯函数——落为同源外置文件（如
`public/assets/aliases.js`、`public/assets/fmt.js`，普通 `src`
脚本、非 module，保持现有执行时序）；S6/S7（行渲染＋原地修补）
永不分离、且与生成管线的关系摸底完成前不拆；拆分批必须单独
成批（不与功能改动、CSP 变体切换、W3-22/F4-46 混批），批内
固定动作：重跑 gen-headers 并 `--check`、snapshot-verify 全过、
部署后 smoke-headers 复验 CSP 实际放行与拆出文件 200。
