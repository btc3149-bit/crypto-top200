## 二、触发线总则

### 2.1 分级（四本账通用）

| 级别 | 通用判据 | 含义 |
|---|---|---|
| 注意 | 用量达到限额的 **≥70%**（按该账重置周期折算：日账看当日量，月账看当月累计或当月投影） | 开始盯紧：加密复核、记录水位，不动生产配置 |
| 警告 | 用量达到限额的 **≥85%**，或投影将在周期结束前撞线 | 执行免费侧先行手段，并向站长汇报水位与投影 |
| 升级 / 撞线 | 投影撞线（预计在重置前耗尽），或已实际撞线 / 已触发平台限流 | 按 §2.2 处置顺序执行；付费选项只能提交给站长决策，不得自行采购 |

CoinGecko 账另有与 W4-02 对齐的投影预警线（优先于通用百分比线判断）：**投影击穿日 ≤7 天警告、≤3 天升级**。投影击穿日 = 按当前日均合计消耗推算，累计用量达到 10,000 credits 的日期距今天的天数。

### 2.2 撞线当天处置顺序（四本账统一，不得跳步）

1. **先核对计量**：先排除计量错误——复核计量来源、统计窗口、是否把探测 / 测试 / 重复部署误计入；计量未核对清楚前，不下「额度不足」的结论、不提扩容。
2. **先用免费手段**：按各账「触发后动作」中的免费侧先行手段逐项执行（降频、减探测、合并 / 延后部署、等周期重置、启用既有降级与缓存等），并记录执行了哪几项、效果如何。
3. **仍不足才提交付费选项**：免费手段用尽后仍投影撞线，才向站长提交付费选项，提交内容必须含：选项名称、当时的官方价格、扩容后的限额、0 元替代方案及其代价（降级程度）。
4. **站长批准后才执行**：**须站长明确批准，未批不采购、不开通**。口头含糊、沉默、或「先开着再说」均不算批准；批准与执行结果记入文末「月度复核记录」表（撞线当月一行，备注栏注明）。
5. **撞线期间的降级是预期行为**：额度耗尽时本站按既有兜底降级（如行情走 stale / 快照），不视为必须靠付费才能避免的宕机；不得以「会降级」为由越过第 4 步。

### 2.3 审批路径（四本账统一）

复核人 / 协调者发现触发 → 记入本文件「月度复核记录」（或撞线当日在该表当月行备注）→ 向站长汇报（水位、投影、已执行的免费手段、付费选项与价格，如有）→ 站长明确批准或否决 → 按批准结果执行 → 执行结果回填记录。决策人始终为站长；复核人 / 协调者无付费采购与开通权限。

- **W4-10 的 prev 版本键上线后 +约 144 写 / 天**（每成功 run +1 次写）。上线后预计约 544–744 写 / 天，上沿将进入「注意」区（≥70%）；**W4-10 上线后的第一次月度复核必须专项复核 KV 写水位**（见「复核节奏」），不得沿用上线前估算。
- **【2026-11-23 W5 修订：按当前生产代码逐 put 点实数】** 对基线 dd16d8c 的 `workers/fetcher/src/index.js` 逐 put 点点数（Cron `*/10` = 144 run / 天）：成功 run = **4 写**——prev 归档（`targetPrevKey`，:522）+ 目标 blob（`targetKey`，:528）+ sourceState（:535）+ health（`writeHealth`，:119）；失败 run（finishFail）= 2 写（health + 有 provider 时 sourceState，:262）；跳过 run（429/额度）= 1 写（health）；CG 探针 run 另 +1 sourceState（:392，现行 CG 主源形态 probeCg=false 不触发）；人工 /run 被拒的 health 写（:625）为事件型、不计入日稳态。**稳态（全成功）= 4 × 144 = 576 写 / 天，占写上限 57.6%，未进入 70% 注意区**——旧「544–744 / 天、上沿进注意区」无代码来源，就此作废。注意：任务背景所称「W5-12 已做 sourceState 变化才写」在 dd16d8c 代码中**并不存在**——:535 仍为每成功 run 无条件写；若日后该优化落地，稳态降至约 432 / 天，届时再按代码复核修订。另 W5 新激活的 legacy 计数键在 legacy/dual 回源时每轮 +1 写（kv 形态 0），代码部署后计入本账、量级不改变 576 的 fetcher 稳态口径。
- 读：当前影子 / legacy 形态下读量低；**G3 切 KV 只读后，读量随 `/api/board` 调用量联动**（每次 board 请求产生 KV 读），届时本账读子账与账三（Functions）同涨同跌，须联动看。

### 计量方法

- 写：以 fetcher 每 run 的 put 点数量 × 当日 run 次数估算；如 Cloudflare 控制台 KV 指标可查当日写量，月度复核时以控制台值为准抄录并与估算交叉核对。
- 读：以 Cloudflare 控制台 KV 指标为准抄录；G3 前读量只抄录不研判，G3 后纳入触发线判断。
- W4-10 上线当月的复核记录备注栏必须注明「prev 键已上线」及上线日期，以便前后水位可比。

### 复核节奏

- 月度复核，动作：①抄录或估算上月每日写量峰值与典型值、读量峰值（G3 后）；②与上次复核的水位对比，写明增量来源（如 W4-10 prev 键、抓取提频——提频本身另有定版约束，见账一）；③判断写、读是否触及触发线；④填入文末「月度复核记录」表。
- 事件复核（不计入月度节奏）：W4-10 上线后、以及 G3 切换后，各做一次专项水位复核并记入同一张记录表（月份行备注注明触发事件）。

### 触发线

- 写——注意：单日写量 ≥700（≥70%）；警告：单日写量 ≥850（≥85%）；升级 / 撞线：单日写量投影或实测将达 / 已达 1,000，或出现 KV 写被限类错误。
- 读——注意：单日读量 ≥70,000（≥70%）；警告：单日读量 ≥85,000（≥85%）；升级 / 撞线：单日读量投影或实测将达 / 已达 100,000。
- 「投影」按当日已过时段的速率外推全天，或按近 7 日峰值趋势外推，口径须在复核记录备注中写明。

### 触发后动作

  2. 减写：合并同 run 内可合并的写、延后非关键状态写；若触发发生在 W4-10 上线后，评估 prev 键的保留策略是否可调（调策略须另经站长确认，不得静默取消版本回退能力）。

## 五、账三：Pages Functions

### 限额

- 100,000 请求 / 天（免费档）。

### 当前水位 / 估算口径

- 当前**无计数台账**（F4-34）：无人计数，水位未知；按现有访问规模定性判断离上限尚远，但「远」无数字支撑——这正是本账要补的缺口，月度复核后改为以抄录数字为准。
- 调用构成：用户访问 `/api/board`、`/api/health` 等 Functions 路径 + **UptimeRobot M2 / M3（各每 5 分钟一次，合计约 576 次 / 天）+ HC1 每小时探针**。探针构成是可算的基线下限，复核时先核对该下限是否与控制台总量同数量级，以此校验计量是否可信。
- G3 后每次 `/api/board` 请求同时产生 KV 读，本账与账二读子账联动（见账二）。

### 计量方法

- **以 Cloudflare 控制台 Analytics 为准，月度复核时抄录**（抄录上月单日峰值与典型日量，注明数据来源为控制台 Analytics）。本账不自建计数代码、不新增线上统计逻辑（W4-22 只动文档）。

### 复核节奏

- 月度复核，动作：①从 Cloudflare 控制台 Analytics 抄录上月 Functions 请求量（单日峰值 + 典型日量）；②拆分估算探针占比（按 M2 / M3 / HC1 的定版频率推算）；③判断是否触及触发线；④填入文末「月度复核记录」表。
- G3 切换后的第一次月度复核须专项注明切换日期，并与账二读量对照（两账应同向变化，背离即先核对计量）。

### 触发线

- 注意：单日请求量 ≥70,000（≥70%）。
- 警告：单日请求量 ≥85,000（≥85%）。
- 升级 / 撞线：单日请求量投影或实测将达 / 已达 100,000，或出现 Functions 超限类错误。

### 触发后动作

- 决策人：站长。审批路径按 §2.3。
- 免费侧先行手段（按顺序先做）：
  1. 核对计量与来源：区分真实用户、监控探针、爬虫 / 滥用流量三类来源占比；来源不清不提扩容。
  2. 减滥用：滥用占主导时，先走既定配额防线（限流 / SFS 等，见 W4-15 的定版处置），不靠扩容对冲滥用。
  3. 减探测：经站长确认后可下调非关键探针频率（代价是监控灵敏度下降，须一并说明）。
  4. 等日重置：日额度接近日界且影响可接受时等次日重置。
- 付费扩容（如免费手段仍不足）：**须站长明确批准，未批不采购、不开通**。提交站长时附当时官方价格与扩容后限额；未批则维持免费档。

## 六、账四：Pages 部署

### 限额

- 500 次 / 月（免费档）。

### 当前水位 / 估算口径

- 当前**无月度计数**（F4-35）：部署次数靠事后翻 git log，答不出「本月已用 / 还剩多少」。
- 历史节奏参考：单批施工可达约 7 次部署（第三期口径）；评审周 / 施工周的部署密度可达每月数十次。按此节奏离 500 次 / 月尚远，但无计数即无预警，本账自建立起按月计数。

### 计量方法

- **计量方法 = git log + CHANGELOG 部署留痕计数，月度复核时统计上月次数**：以 git log 中部署相关提交与 CHANGELOG / 签收留痕中的部署记录交叉计数，两边对不上的逐条核对并在复核记录备注中说明差额原因（如 preview 部署、回滚部署是否计入——口径一经确定不得逐月变更，变更须在备注中注明）。

### 复核节奏

- 月度复核，动作：①按上述计量方法统计上月部署总次数；②标明上月部署最密集的一周及其事由（施工批 / 评审 / 故障修复）；③按当前施工排期投影本月部署次数；④判断是否触及触发线；⑤填入文末「月度复核记录」表。

### 触发线

- 注意：当月累计部署 ≥350 次（≥70%），或投影全月 ≥350 次。
- 警告：当月累计部署 ≥425 次（≥85%），或投影全月 ≥425 次。
- 升级 / 撞线：投影全月将达 / 已达 500 次，或平台提示部署额度受限。

### 触发后动作

- 决策人：站长。审批路径按 §2.3。
- 免费侧先行手段（按顺序先做）：
  1. 核对计量：确认 preview、回滚、失败重部署是否被重复计数，口径与上月一致。
  2. 合并部署：非紧急改动攒批合并为一次部署；紧急修复部署不受此限，但须在复核记录中注明事由。
  3. 延后非紧急部署：接近月末且投影撞线时，非紧急部署延至下月额度重置后。
  4. 等月度重置：部署额度按月重置，延后成本通常低于任何扩容成本，优先采用。
- 付费扩容（如免费手段仍不足）：**须站长明确批准，未批不采购、不开通**。提交站长时附当时官方价格与扩容后限额；未批则维持免费档并按上述合并 / 延后手段执行。
