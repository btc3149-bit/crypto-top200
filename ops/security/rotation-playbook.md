## §20.2 K2 CoinGecko key 轮换剧本（双路径）

### ⚠️ 步骤 0（流程硬规则，先于一切操作，醒目执行）

> **新 key 的值只许经保险箱安全采集页录入，禁止再走聊天消息、截图、文档粘贴。**
> 2026-11-10 的暴露正源于安全表单误报后改走聊天——本期起，表单校验失败时的正确动作是**停下报错、换采集方式，不许降级到明文渠道**。此条同步写入 README 红线区（由协调者统一合入）。

### 步骤 1（用户在 CoinGecko 控制台操作，助手给分步指引）

登录 CoinGecko（账号为用户自选的 Google 账号）→ Developer Dashboard → 尝试 **+ Add New Key**：

- **路径 A（增发成功——以施工当日实测为准）**：Demo 档定价页写全账号 1 把 key，但控制台实际策略以当日为准，故先试。若允许第 2 把：命名 `top200-prod-202611`（月份后缀便于台账对账）→ 走步骤 2–5 无缝切换 → 最后吊销旧 key。切换全程双 key 有效，零窗口。
- **路径 B（增发被拒，预期路径）**：同一 key 槽位删除旧 key → 新建 key（命名同上）。从删到新 key 注入完成之间上游调用必然失败——兜底来自 W2-01 的 KV 最后成功快照：`/api/board` 继续出 stale 数据并打 stale 标记，用户侧无感（仅新鲜度降级）。执行窗口选在 Cron 刚成功跑完一轮之后（快照最新），全程目标 ≤15 分钟。若 W2-01 尚未上线、现形态仍是请求时现拉，则路径 B 须先排在 W2-01 之后，或接受分钟级 `/api/board` 报错窗口并在低峰执行——**排序定版：K2 轮换与 W2-01 同窗口、紧随其后**。

### 步骤 2（注入新 key）

经保险箱更新后，由部署通道执行（命令中的值不出现在聊天/日志/脚本文件里）：

```bash
npx wrangler pages secret put COINGECKO_API_KEY --project-name crypto-top200
# 交互式粘贴新 key 值；禁止用 echo/参数明文传值（会进 shell 历史与进程列表）
```

注意：Pages Secret 变更**需重新部署才对 Function 生效**——紧接步骤 3，不得只 put 不 deploy 就宣布完成。

### 步骤 3（重新部署）

走现行 Wrangler 直推管线（与 W2-11 合并后即管线一键）；部署产物须同时包含 W2-18 的 `_headers` 时按其流程，不得为轮换单独绕过生成步骤。

### 步骤 4（线上验证，无感验收标准）

- 手动触发一次 Cron（或等最近一轮）后查 `/api/board`：`mode=live`（或 W2-01 定版的新鲜度字段等价物）、`updatedAt` 为切换后的新时间、覆盖 200/200 与切换前一致；
- CoinGecko 控制台用量图出现新 key 名下的调用记录；
- （路径 B 追加）旧 key 直连探针：以旧 key 值对 `https://api.coingecko.com/api/v3/ping` 发一次带 `x-cg-demo-api-key` 头的请求，须返回 401/403——证明旧值确已失效（旧值已暴露，此探针不产生新的保密问题；探针在本地执行、旧值不进任何留痕文件）；
- 切换后 24 小时观察：`/api/board` 无因额度/鉴权导致的异常波动。

### 步骤 5（吊销与收尾）

路径 A 在步骤 4 全过后于控制台吊销/删除旧 key，并复跑一次旧 key 探针确认失效；更新密钥台账（K2 行：轮换日期、新 key 名称、下次轮换期 §20.6）；事件记录入合规留痕。

### 回滚

新 key 若验证不过（额度未生效、控制台状态异常），回滚 = secret put 回旧 key 值 + 重新部署（路径 A 旧 key 尚在，回滚干净；路径 B 旧 key 已删不可回滚——这正是路径 B 须在步骤 1 先把新 key 在控制台**直连探针验活**（本地 curl 通了再删旧槽位/再注入）的原因，探针未过不许动生产 Secret）。

## §20.3 Preview 环境独立 key 改判（定版：fixture）

一期 P2-2「双环境各一 key」的前提（同账号可多 key）已被证伪（Demo 档 1 把，Basic 仍 1 把）。三条出路的取舍：再注册第二个账号（否决：一人多号领免费额度，与平台意图相悖且台账翻倍）；双环境共用同一 key 值（否决：假隔离，额度共享、泄露面翻倍、轮换易漏一处）；**Preview 零 key 走 fixture（采用）**。

**Fixture 定版**：

- Preview 环境不配 `COINGECKO_API_KEY`；Function 在 Preview 上下文读仓库内固定的样例快照（或构建时注入的一份脱敏 board JSON），以 `mode=fixture` 标识。
- fixture 数据取一份真实 board 快照的结构，数值可保留（本就是公开行情），但**须带固定旧时间戳**以免被误当实时。
- W2-18 冒烟脚本对 Preview 的断言相应调整为「fixture 标识在位、行数齐」，不查 `updatedAt` 新鲜度。
- Preview 的真实用途是验 UI/CSP/冒烟，不验上游新鲜度；零 key = 零额度消耗、零泄露面，预览结果还可复现。
- 将来若升付费高阶档（10 key），届时再启用真·双环境独立 key，并回写本节。

### K3 `MANUAL_RUN_TOKEN` 轮换与吊销流程

该 token 为单一静态值、无平台侧吊销开关，**换值即吊销**：

1. 由站长生成新值，只经保险箱安全采集页录入（同 §20.2 步骤 0 硬规则，禁止走聊天/截图/文档明文）；
2. 更新 fetcher Worker Secret（`MANUAL_RUN_TOKEN`，Worker `crypto-top200-fetcher`）并重新部署 fetcher——新 Secret 生效后旧值立即失效，此即吊销完成点；轮换窗口内 `/run` 手动触发短暂不可用属预期（定时抓取不受影响）；
3. 验证：以新值调一次 `POST /run` 须被接受，以旧值再调须被拒绝（401/403）；两项都过才算轮换完成；
4. 收尾：更新台账 K3 行（轮换日期、下次动作点顺延 6 个月、状态改为已轮换）并留痕；疑似泄露时按同一流程立即执行，并在留痕中注明触发原因。

**执行留痕（2026-11-13，站长授权后由助手执行）**：已按本流程完成一次轮换，新值经 `secret put` 注入、`secret list` 回读在位、旧值即刻失效，台账 K3 行已更新（下次 2027-05-13）。两处口径注记：①新值由助手生成并只经 stdin 注入（同 W2-01 初值形态），全程无明文出现在聊天/文档/日志，不违步骤 1「禁止明文渠道」的本意；②步骤 2 的「重新部署 fetcher」在本地代码与线上不一致（有未放行改动）时**禁止顺带执行**——secret put 本身即完成换值与吊销，部署另走门禁。本轮步骤 3 的 `/run` 实测因沙箱直连 workers.dev 被边缘 1010 拦截、且 G1 观察窗纪律禁触发抓取而未做，台账已如实标注，留待 G1 结算后按需补验。
