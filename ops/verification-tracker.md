## 二、自选跨设备限制书面定版（F4-47）——已知接受项，非缺陷

**定版结论：自选只存浏览器 `localStorage`、换设备/换浏览器/清缓存
即丢失、无跨设备同步——此为已知接受项（accepted limitation），
不是缺陷，后续评审/施工不得再以缺陷形式重提；重提的唯一合法路径
是站长推翻「不做账号系统」的既定决策并单独立项。**

- 现状证据（基准提交）：`public/index.html:459`
  `WATCH_KEY = "top200.watchlist.v1"`；`:460-481` `loadWatch`/
  `saveWatch` 只读写本机 `localStorage`，全仓无任何把自选上传到
  服务器的代码或接口。自选数据从不离开用户本机（与隐私页第五节
  承诺一致，见 `ops/privacy/wa-consistency-table.md` P-20）。
- 接受依据：项目既定决策「不做账号系统/登录」
  （`PHASE4_REVIEW.md` 第四节「明确不做清单」第 2 条：自选跨设备
  同步不做、不收集用户账号信息）。无账号即无服务端身份锚点，
  跨设备同步在技术上无处挂靠；为一个本地收藏清单引入账号系统，
  成本与隐私面（开始持有用户身份数据）都与本站「公开榜单、无账号」
  的定位相悖。
- 用户侧影响与已有提示面：换设备/清缓存后自选清空，需重新点选；
  影响上限是「重新点一遍星标」，无数据资产损失。隐私页第五节已
  向访客说明「只保存在本机、清除浏览器站点数据即可删除」，
  行为与说明一致。
- 重开条件（满足才可重议，且须站长单独拍板）：站长明确决定引入
  账号系统，或出现不依赖账号的同步载体且站长点名要做。在此之前，
  任何工作包不得以「顺带」方式给自选加服务端存储。

## 三、详情后退行为定版方案（F4-46）——方案已定版，实现待后续批次

### 现状（问题复述，代码实查）

- 展开/关闭详情时写 hash 的唯一落点是 `syncHashForExpand`
  （`public/index.html:800-811`）：打开时
  `history.replaceState(null, "", "#" + c.symbol)`（:802），关闭时
  `history.replaceState(null, "", "/")`（:806）。
- `replaceState` 不产生历史条目：用户从外部/首页进入、点开详情后
  按手机系统后退键（或浏览器后退），不会回到「详情关闭的榜单」，
  而是直接离开本站。这与移动端用户「后退＝关掉当前这一层」的
  普遍预期相悖（F4-46 原文）。
- 现有 hash 语义同时被单币直达功能占用：`parseHashTarget`/
  `applyHashTarget`/`onHashChange`（`public/index.html:979-1023`）
  在加载与 `hashchange` 时按 `#币种` 定位、展开并 flash 目标行，
  且 `hashchange` 监听已注册（:1094）。改历史行为必须与这套
  语义联动设计，不能只换一个 API 名。

### 定版目标方案（pushState ＋ popstate 关详情）

1. **打开详情时入栈**：`syncHashForExpand` 打开分支改为——若当前
   `location.hash` 尚未等于该币种 hash，则
   `history.pushState({ top200Detail: <coingeckoId> }, "", "#" + symbol)`
   写入一条历史；若 hash 已是该币种（典型：用户经直达链接进来、
   或重复展开同一币种），**不重复 push**，只保持展开状态。
2. **后退时关详情**：新增 `popstate` 处理——当后退使 hash 离开
   当前展开币种（hash 变空或变为其它值）时，关闭对应详情行
   （复用 `toggleExpand` 的关闭路径渲染，但**不得在关闭动作里
   再写任何 history**），并恢复默认标题。处理须与既有
   `onHashChange` 分工写死：`hashchange` 继续管「新 hash 指向某币
   →定位展开」，`popstate` 管「后退离开→关闭」，同一手势不得
   两路重复触发（以既有 `applyingHash` 标志位或等效守卫去重）。
3. **界面内关闭的语义对齐**：用户点展开按钮主动关闭详情时，
   若当前历史条目是第 1 步 push 的那一条，应走 `history.back()`
   让栈与界面状态一致（由随后的 popstate 完成实际关闭渲染）；
   若不是 push 来的条目（直达进入后手动关闭），维持现行
   `replaceState` 清 hash 的做法，不后退离站。
4. **直达链接不回归**：带 `#币种` 首次加载时不额外 push
   （落地页本身就是栈底），此时后退离站是正确行为；直达的定位、
   展开、flash、document.title 更新行为与现行完全一致。

### 风险与交互清单（实现批次必须逐项回归）

| 风险点 | 说明 | 处置要求 |
|---|---|---|
| 与单币 hash 直达的交互 | 同一 `#币种` 既是「可分享的直达地址」又是「详情打开状态」，push 后复制地址分享、刷新、前进/后退交错时容易出现重复展开或栈内多条同 hash | 用例表覆盖：直达进入→后退（离站，正确）；首页进入→开详情→后退（关详情留站）；开 A→开 B→后退两次；直达进入→手动关→后退（离站且无残留状态） |
| 多详情同时展开 | 现行 `expandedIds` 是集合、可多开；hash 只能表达一个币种。push 模型下「当前 hash 对应哪个详情」须有定版口径 | 实现批次定版口径（建议：hash 只跟随最近一次打开的详情；后退只关闭该一个，其余展开不动），并写进用例 |
| popstate 与 hashchange 双触发 | 后退改 hash 时两事件都会来；现行 `onHashChange` 会尝试按新 hash 展开，与「关闭」目标可能打架 | 以守卫标志去重并明确两事件分工（见方案第 2 步）；桩测须模拟该序列 |
| flash 清除与焦点 | 现行有 pointer/wheel/input/keydown 时清 flash 的监听与焦点管理（`clearFlash`、Esc 关详情） | popstate 关闭路径须复用同一套渲染/焦点逻辑，不另起分支 |
| 桌面端 | 桌面后退键/鼠标侧键同样走 popstate，行为应与移动端口径一致 | 桌面浏览器列入实现批次的回归环境，不只测手机 |
